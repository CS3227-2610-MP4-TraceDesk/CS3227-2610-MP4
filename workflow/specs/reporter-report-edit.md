# REPORT-EDIT — Reporter drafts and version-safe report editing

Status: bounded implementation contract for [issue #15](https://github.com/CS3227-2610-MP4-TraceDesk/CS3227-2610-MP4/issues/15); not an implementation or completion record. Human owner: not supplied. This contract derives its field, ownership, lifecycle, storage, retention, API, and transaction behavior from [TD-RPT](reporter-reports.md), especially “Report and draft data contract,” “Lifecycle and allowed mutation,” “Interfaces,” “Idempotency, transactions, and audit,” and TD-RPT-01–05. It refines the implemented [REPORT-UI](reporter-workspace-ui.md) and the approved [product scope](../../docs/product.md), [shared role contracts](../decisions/002-shared-role-contracts.md), [architecture](../../docs/architecture.md), and [security contract](../../docs/security.md). It does not authorize deployment, account or project provisioning, or AI/provider integration.

## Goal and boundaries

A Reporter can explicitly save a private, server-persisted draft, return to it from the same project, delete it, or submit it as a new `OPEN` report. A Reporter can edit the seven shared fields on their own report only while its status is `OPEN`. Every saved report or draft update uses the expected row version. The backend remains authoritative for identity, membership, object ownership, lifecycle, validation, and persistence. Drafts are not a lifecycle status.

Drafts are saved only through an explicit user action. Do not autosave, persist report text in browser storage, or treat a partially entered unsaved form as a draft. Reuse the canonical field values and exact limits from TD-RPT; no new field, retention rule, role permission, or lifecycle edge is introduced here. Draft submission creates a report using the canonical submission contract; it is not a second report-edit path.

The current #14 UI provides the Reports list, detail, and new-report composer. The current report API provides create, list, detail, and Reporter context; `ReportController`, `ReportRepository`, and `ReportStore` have no edit or draft operations. The #13 migration stores reports and report-creation idempotency, but this slice still needs persistent draft storage and the necessary mutation audit behavior. No application API or migration for drafts/editing is present in the inspected candidate. Implement against the canonical interfaces below; do not add a client-side mock as a substitute.

## Identity, access, and lifecycle

Resolve the actor from the current server-side session. For every list, read, create, update, delete, or submit operation, check the current enabled user, enabled project, active membership, role, and object visibility from trusted server state. Never accept actor, role, ownership, project, status, assignment, timestamps, version, or audit metadata from a writable body. Recheck and lock the membership and target row inside mutations so revocation serializes with the operation.

- A Reporter may list/read/delete/update only their own unexpired drafts in the selected project. Drafts are never visible to another user or to Developer/QA members.
- A Reporter may edit only their own report while it is `OPEN`. All seven shared fields are replaced together. Reporters cannot change status, assignment, owner, project, or lifecycle. A visible report in another lifecycle state rejects editing with `409 INVALID_STATE`.
- An active Developer or QA reviewer may read shared report fields as already defined by TD-RPT, but cannot edit Reporter fields. A role without the action receives `403 FORBIDDEN`; a report/draft that is absent, cross-project, or invisible to that actor returns the opaque `404 NOT_FOUND` response.
- A disabled user/project, inactive or removed membership, or non-member receives the canonical opaque 404. Membership role changes remove Reporter draft/edit permissions immediately after the authorization point.
- A draft remains private to its owner and project across logout. Sign-out, account change, project change, and authorization denial clear the previous account/project's in-memory form, selection, and response data; they do not delete a server draft. On a later authorized sign-in, the owner can list and resume it. No client role selector or cached role grants access.

## Data and persistence contract

Use all seven canonical fields and their established limits: `title` 160 code points/640 UTF-8 bytes; `description` 10,000/40,000; `environment` 4,000/16,000; `reproductionSteps` 8,000/32,000; `expectedBehavior` 4,000/16,000; `actualBehavior` 4,000/16,000; and optional `textLogs` 16,000/64,000. Enforce the 184,640-byte aggregate text maximum and 256 KiB JSON request cap. Reject unpaired surrogates, NUL, and C0/C1 controls except TAB, LF, CR. Preserve exact decoded values and line endings; do not trim, normalize, truncate, or interpret as markup. A submitted report requires the six canonical nonblank fields. Draft fields may be empty.

Draft records have UUID, project UUID, owner UUID, the seven fields, `createdAt`, `updatedAt`, `expiresAt`, positive `version`, and nullable `submittedReportId`. A new draft starts at version 1. Its 30-day expiry is measured from creation; subsequent saves update `updatedAt` and version but do not extend its original expiry. Expired drafts are unavailable immediately and may be purged later. A submitted draft remains immutable and available to its owner until its original expiry, with its link to the created report. Permit no more than 20 unexpired drafts per `(owner, project)`; the 21st returns `409 DRAFT_LIMIT`. Explicit deletion is owner-only, version-checked, and permanent. Do not expose draft existence across users or projects.

Use fresh TraceDesk migrations and isolated synthetic test databases. A database migration must enforce owner/project foreign keys, field bounds and safe text rules, positive version, expiry/link consistency, and at-most-one report submitted from a draft. Store only bounded metadata and digests in idempotency/audit records; do not duplicate user content there. Every successful mutation and its business audit event commit atomically. A required audit/security-event sink or persistence failure returns `503 SERVICE_UNAVAILABLE` and commits no partial mutation.

## Interfaces

All routes use the existing same-origin session and CSRF protections. State changes require `X-CSRF-TOKEN`; create and submit also require a canonical UUID `Idempotency-Key`. Request bodies contain only the permitted fields and command version. Reject unknown/duplicate keys, nulls, wrong types, and server-owned fields. Reads are bounded and `Cache-Control: no-store`.

| Operation | Request | Success |
| --- | --- | --- |
| `POST /api/projects/{projectId}/drafts` | Any/all seven fields; idempotency key | `201` owner draft, version 1 |
| `GET /api/projects/{projectId}/drafts?limit=&cursor=` | Canonical bounded pagination; owner only | `200 {items,nextCursor}` with summaries only, fixed `updated_at DESC, id DESC` order |
| `GET /api/projects/{projectId}/drafts/{draftId}` | None | `200` owner draft with fields and version |
| `PATCH /api/projects/{projectId}/drafts/{draftId}` | All seven fields plus `expectedVersion` | `200` updated owner draft |
| `DELETE /api/projects/{projectId}/drafts/{draftId}?expectedVersion=` | Positive expected version | `204` |
| `POST /api/projects/{projectId}/drafts/{draftId}/submit` | `expectedVersion`; idempotency key | `201` created report representation plus `submittedDraftId` |
| `PATCH /api/projects/{projectId}/reports/{reportId}` | All seven fields plus `expectedVersion` | `200` updated report representation |

Draft list pagination reuses the canonical TD-RPT limit (1–100, default 25), signed actor/project/purpose-bound cursor, 15-minute expiry, and fixed ordering. The summary allowlist is `id`, `projectId`, `title`, `createdAt`, `updatedAt`, `expiresAt`, `version`, and `submittedReportId`. A draft detail contains only its canonical ID, project ID, owner fields, UTC timestamps, expiry, version, and submission link; do not return login, session, role, other drafts, or unrelated project data.

For draft creation, the idempotency record is scoped by trusted actor, project, operation, and key for 24 hours and stores the validated canonical-body SHA-256 digest, not text. A same-key/same-body retry returns the same draft ID and freshly authorized current representation without another mutation/audit; a changed body returns `409 IDEMPOTENCY_CONFLICT`. If an explicitly deleted draft is replayed, return `404 NOT_FOUND`.

Draft submission uses the canonical command body (`draftId` from the route plus `expectedVersion`). In one transaction it rechecks owner, project, expiry, complete-report validation, version, and unsubmitted state; creates exactly one `OPEN` report; links and versions the immutable draft; writes the idempotency record; and writes one submission audit event. Same-key/same-body retry within 24 hours returns the same report's current authorized representation without a second mutation/audit, even if the draft was later purged. A different key after successful submission returns `409 DRAFT_ALREADY_SUBMITTED`, identifying the existing report only to its authorized owner. Replays always reauthorize; expired keys have no replay guarantee.

Report and draft `PATCH` requests use optimistic concurrency through `expectedVersion`, not idempotency. A mismatch returns `409 STALE_VERSION` with only the current authorized representation's version, without applying fields or writing a mutation audit. A successful update increments that row's version exactly once and updates its timestamp. On a concurrent race, exactly one request with a given expected version may commit; the loser receives the stale response. The mutation, fresh membership/object/state check, version change, and metadata-only audit are one transaction.

Use the existing error precedence and safe JSON envelope in TD-RPT. Framing/path/shape errors are generic `400 INVALID_REQUEST`; state-changing requests validate CSRF before session/business state; unauthenticated is `401 UNAUTHENTICATED`; inaccessible objects use opaque `404 NOT_FOUND`; recognized but disallowed roles use `403 FORBIDDEN`; disallowed report lifecycle uses `409 INVALID_STATE`; invalid fields use `400 VALIDATION_ERROR`; stale versions, idempotency conflicts, draft limit, and already-submitted drafts use their specified stable 409 codes; authorized expired draft uses `410 DRAFT_EXPIRED`; storage/audit/session-store failure uses `503 SERVICE_UNAVAILABLE`. Never echo submitted values or include report text in audit/security events, logs, or generic errors.

## UI behavior and recovery

Extend the existing Reports workspace and shared controls; do not add a new portal. Show the current project's saved drafts in Reports with clear draft labeling, saved time/expiry, and Resume/Delete actions. “Save draft” is explicit and leaves field values visible; it gives a confirmed saved state only after a valid server response. Resume fetches the current authorized draft by ID/version. Deletion requires explicit confirmation and the displayed draft version; stale/expired/denied outcomes refresh only after authorization and never claim deletion without `204`.

Editing a saved report starts from the actual authorized detail representation and its version. Keep all fields in the form, but expose an edit action only while its server-returned status is `OPEN`; the server remains decisive if state changed after display. A successful save opens/displays the actual returned representation and new version. A known validation/state/access failure preserves the user's input and reports the safe outcome. A timeout or connection loss after a `PATCH` is ambiguous: re-read the authorized object before offering another save; do not blindly resubmit an old expected version or announce success without a confirming representation.

For `409 STALE_VERSION`, keep the reporter's unsaved values in memory and explain that a newer version exists. Fetch the current authorized representation and show the server values alongside the local edits so the user can review what changed. Offer explicit choices to discard local edits and load the current version, or keep the local values and submit them against the newly displayed version after the user has reviewed the whole-record replacement. Never auto-merge, auto-retry, or silently overwrite another saved change. A repeated conflict returns to this review step. If refresh fails, preserve the local edits and provide retry without reverting to a false “saved” state. Do not place report or draft text, credentials, session/CSRF data, or user identity in localStorage, URLs, console, telemetry, or client logs. Render all returned text as escaped plain text.
